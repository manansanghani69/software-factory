# Terminal-first driving surface

The Factory's primary — and in v1, only — driving surface is the terminal session: a thin `factory` CLI plus the agent sessions the inherited skills already inhabit. The `factory` command exposes a day brief, idea entry, request intake, ticket claiming, and state peeking. A web dashboard is deferred: github.com's tracker UI already renders the map, frontier, and blocking natively (per ADR 0001), so a bespoke dashboard in v1 would duplicate what the Operator can already see. The dashboard returns when the Factory program exists and is actually driven, at which point it can be built from the program's own server.

Web-first was rejected because driving the Factory means driving agents, and agents live in terminal sessions today; building a browser-driven agent runtime for v1 would mean re-implementing HITL gates and session orchestration in-browser — significant scope with no payoff for a single operator. Both-first-class was rejected for the same reason: two real surfaces before you know which you'll use doubles the v1 surface for one person. The terminal-first choice is surprising (Products are web apps, the Operator lives in a browser), so this ADR records the trade-off.
