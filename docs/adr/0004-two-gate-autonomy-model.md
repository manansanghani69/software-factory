# Two-gate autonomy model

Every stage of the Line is either **driven** — the Factory runs it alone and reports, never blocking — or **gated** — the Line stops until the Operator decides. The v1 gates sit at the end of spec and at review; sharpening, tickets, implementation, and ship are driven stages. The spec gate lands before implementation burns budget, the cheapest place for the Operator to correct course; the review gate exists because a Product is a web app the Operator must actually run and see. Within implementation, ticket selection is itself driven by the frontier logic — the Operator does not pick tickets.

Review, the stage where the Factory checks its own code, is three-layered: automated checks (tests, lint, typecheck, build); a review agent independent of the code's author, checking the diff against the spec and the repo's standards; then the Operator at the gate, seeing the running app. The gate asks a disposition — advance (ship), revise (back up the Line), halt (off-track for a reason beyond code) — and ship rides it: there is no third gate. A driven stage that hits something it wasn't briefed to decide stops and reports the fork with options rather than guessing.

Gate-at-every-stage was rejected: for a sole Operator it turns the Factory into a manual tool and rows against the Fork machinery, which already exists to turn work into agent-ready tickets. Gate-only-at-ship was rejected: mis-sharpened or mis-specified work is cheapest to catch before implementation spends its budget, and review-after-ship reaches the Operator too late to satisfy "the app the Operator must see."
