# Agent orchestration internals

The Factory program drives a Product Line as **one Mastra workflow per Line run** — one effort's pass down the Line, from Idea to ship or halt — suspended at the gates and resumed across restarts by `runId`. The workflow's steps are the driven stages (sharpening → tickets → implementation → ship) interleaved with the spec and review **gate steps** that `suspend()` for an Operator disposition and resume. Artifacts ride the workflow state across days-long gates; fan-out inside a stage (per-ticket implementation, the review bar's parallel checks) uses `.parallel()` / `.foreach()`. Per-stage sessions were rejected: they re-implement the handoff and the gate mechanics at every boundary for no gained capability.

**Each Line stage is one Mastra agent**, wired into its workflow step, with its own instruction set and tools. Mastra subagents are reserved for genuine in-stage splits — above all the review bar, where the reviewer agent must be independent of the author agent — not as a general orchestrator-workers layer (the Line is linear; an orchestrator would only add indirection). A single agent swapping instruction sets per stage was rejected: it bleeds the skills together and bloats context.

**Models route through a table keyed by stage** in `.factory/config.json` — defaults baked into the code, each stage overridable at runtime by env (`FACTORY_MODEL_<STAGE>=provider/model`) and by the config file, with no rebuild. v1 defaults every stage to `anthropic/claude-sonnet-4-6`, the model the First Slice prototype ran with; the table is the seam where a cheaper, faster model for high-volume driven stages would later land. Mastra binds one model per agent at construction and resolves `provider/model` strings to provider env keys (`ANTHROPIC_API_KEY`, `OPENAI_API_KEY`, `GOOGLE_API_KEY`), so a string change is the whole routing change. Per-request dynamic routing (`model` as a function of `requestContext`) is deferred: nothing in v1 needs it.

**The inherited skill markdown files plug in as agent instructions through a stage-instruction loader**: at agent registration, the loader composes each stage agent's `instructions` from the fork's in-repo skill files — the stage's `SKILL.md` plus the reference files it points at. This is the First Slice prototype's mechanism (sharpening prompt → sharpening agent) made compositional; reading at registration (not baking skill text into source) means a fork edit takes effect on restart. Mastra's own `skills` loader was deferred pending a format match; read-to-string keeps no dependency on it.

**Workflow runs persist durably to `@mastra/libsql` (SQLite) at `.factory/state/workflows.db`** (gitignored), sitting beside the Factory's other local state. Mastra defaults to a non-durable in-memory store that loses every suspend/resume snapshot on restart — unfit for runs that wait days at a gate — and `@mastra/pg` adds a service to run for a sole Operator. SQLite is the ceiling the Factory needs today, with the storage interface holding the seam to Postgres if query load ever grows.
