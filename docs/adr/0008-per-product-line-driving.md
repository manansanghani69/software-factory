# Per-Product Line driving

The Factory program drives each Product's Line from this repo as a **central controller**: it discovers Products by scanning sibling directories for the seeded `.factory/state/product.json` — registration *is* the file, no registry to keep in sync — and keeps every Product's run state in the Factory repo's `.factory/state/` (workflows.db keyed per Product). This makes "the Factory repo's CLI reading a Product repo's state" literal. Per-line operating contexts were rejected: driving from inside each Product's clone scatters the Operator's run state and contradicts the settled phrasing.

**A Line's position is derived, never stored authoritatively.** The current stage is read from what is already true: the live run in workflows.db (a suspended run is *at* that gate or fork) plus the Product tracker's open issues and labels. `product.json` keeps identity and stack; its `line.*` fields are a best-effort mirror the Factory refreshes on transitions, for human eyes and the scaffold's promised shape only. A stored stage field would be a third authority that can only drift from the run and the tracker.

**Gates surface through the day brief and `factory open <product>`.** The bare `factory` command scans the discovered Products and reports each Line's position — which gate it is suspended at, or a fork awaiting a pick — read locally from run state plus a `gh` read of the Product tracker. `factory open <product>` attaches to the suspended run, shows the evidence bundle, and resumes it with the Operator's disposition. The Operator names the Product; the CLI never makes them juggle repos.

**Driven stages leave stage reports; gates bundle evidence.** Every driven stage posts a stage report as a comment on the Line's current issue in the Product tracker (the spec at the spec gate, the ticket list after ticket-generation, an implementation summary, the reviewer's checklist at review), and the day brief digests it at a glance. Gates present the ADR 0006 evidence bundle: spec + automated results + reviewer report + running-app URL.

**Per-stage behavior under the controller:** sharpening opens an idea issue in the Product tracker and runs a Line run to the spec gate; advance/revise happens there; on advance, tickets are generated in the Product tracker from the spec; implementation picks frontier tickets itself (per ADR 0004) and works in the Product's sibling checkout on a per-run branch, pushing a PR; the review step runs the automated bar in the checkout against the PR branch — red auto-revises inside the run without the Operator, under the halt cap — the independent reviewer (ADR 0007 subagent) checks the PR diff, then `factory open <product>` boots the dev server and shows the running app with both reports; advance merges the PR on a green bar. Ship is merge; Vercel deploy stays documented-only per the Web-App Scaffolding decision.

**A fork is a stage-raised stop, distinct from a gate.** A driven stage that hits a decision it wasn't briefed to make forks: it suspends the run (same suspend/resume machinery as a gate, surviving restarts), posts a fork report on the current issue — what it was asked to decide, what it found, the options it can see with their consequences, and its recommendation — marks the issue so the day brief finds it, and awaits an option-pick through `factory open <product>`. If the Operator's pick isn't among the options, the run re-forks with the new instruction. Gates are scheduled stops with known choices; forks are unbriefed stops the stage raises.
